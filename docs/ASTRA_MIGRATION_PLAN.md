The following steps are future work for Hermes. None was executed in this pass.

Verify whether main's icon migration is live. Save a restorable Postgres backup outside the repo and test restore into an isolated Postgres database. Preserve the current production image and environment configuration. Do not print tokens or connection strings in logs.

2. **Establish ownership without blocking engineering.** Open an owner continuation branch from current main in a separate checkout; leave this working tree untouched. Port wd's migration selectively, retaining attribution (e.g. cherry-pick with provenance and resolve against main, then review the entire resulting diff). A direct cherry-pick is only a starting point: preserve icon support and all other intervening features. Draft a linked successor PR explaining it incorporates #1. Percy/Hermes should communicate the handoff before posting or closing anything; this read-only task sends no messages. Invite wd to review; do not require an unknown wait to continue. Close #1 as superseded once the successor is concrete, not as rejected work.

3. **Prevent accidental production deployments first.** Pin Railway to its known-good deployment or disable its main auto-deploy before any migration merge. The retained Dockerfile invokes Prisma generation and Next build; Railway startup invokes Prisma migration, but the PR removes Prisma dependencies and changes database runtime. A main push must not redeploy that code to Railway. Change Cloudflare deployment from unconditional main push to explicit staging and controlled production promotion, with one concurrent deployment per environment and no cancellation halfway through migration. Keep DNS mutation outside routine app deployment.

4. **Create isolated Cloudflare resources.** Confirm the owner account ID. Using a pinned, verified CLI, create `fra-db-staging` and a separate empty production candidate such as `fra-db-prod-20260930`. Concrete Wrangler equivalents are `wrangler d1 create fra-db-staging` and `wrangler d1 create fra-db-prod-20260930`; record returned UUIDs. These are templates for later execution, not commands run here. Assign distinct Worker names and ensure each `DB` binding resolves to its intended UUID. Never reuse staging data as production. Assert identity via account/database metadata and row/schema checks before every migration/import. Do not assume editing `wrangler.toml` changes what `cf` deploys from `cloudflare.config.ts`.

5. **Repair code and runtime setup.** Initialize/configure the version-matched vinext + RSC + Cloudflare Vite plugins in a committed `vite.config.ts`, resolving configuration against the locked versions rather than copying a latest-version example blindly. Choose one authoritative deployment configuration and remove or clearly separate conflicting legacy config/scripts. Pin a supported Node 22 patch and dependency lock. Generate real Workers binding types before type-checking; retire hand-written `any` stubs. Keep database I/O in request handling.

   For profile creation, compute the profile ID, seed IDs, and timestamp in advance. Execute the profile INSERT and all seed INSERT chunks in **one D1 batch transaction**. Five bound values per card allow at most 20 cards per INSERT; 195 cards need 10 INSERT statements plus the profile statement. Count actual generated parameters, including any extra clauses. Separate awaited chunk writes are not atomic. Catch the actual unique-constraint failure and return 409; the precheck alone races. Do not use compensating profile deletion as the primary atomicity mechanism.

   For imports, fix both multi-row INSERTs and the existing lookup `profileId = ? AND name IN (...)` (at most 99 names when that predicate has one additional parameter). Replace sequential quantity updates with a bounded atomic batch, preferably conflict-safe upserts that preserve existing IDs and owned state while increasing quantity. Preserve response semantics for added/updated counts. Reject oversized requests before any write if limits cannot be met. Never silently split one atomic user action across committed batches. Test concurrent imports and ambiguous-response retries: incrementing imports are not inherently idempotent.

   Order matches descending in SQL before LIMIT, with a stable tie-breaker. Audit every generated INSERT and `inArray`, including match deck/player lookups: 100 matches can reference more than 100 distinct decks. Preserve `iconCard`, API shape, deletions, deck constraints, and current UI behavior. Treat the pre-existing catalog total discrepancy separately unless a minimal correction is needed for truthful verification.

First verify no database whose history matters has applied that lineage. Do not rewrite migrations already applied to a shared/live database. Apply schema before data using an explicit remote target, e.g. pinned `wrangler d1 migrations apply <database-name> --remote` with the selected configuration's `migrations_dir`. Test remote D1, not just SQLite. No data import should trigger the PR's `0001` table rebuild afterward.

Set `CLOUDFLARE_ACCOUNT_ID` and the correct environment-specific database identifier (`D1_DATABASE_ID` if keeping that workflow input). IDs need not be secrets, but must be consistent across CLI and binding config. The running Worker uses a D1 binding, not a GitHub PAT or Postgres `DATABASE_URL`. Keep Postgres export credentials in the migration operator environment only. Restrict production secrets/deployment to trusted reviewed refs; staging cannot use production data-write credentials. Avoid untrusted fork code running with secrets. Use explicit remote/noninteractive CLI options supported by the pinned version.

8. **Rehearse end-to-end on staging.** Future implementation checks: clean `npm ci`, generated types, type-check, actual Worker build, and remote deployment at a separate preview hostname. Verify post-write reloads show fresh data. A static health response is insufficient: run a database-backed readiness probe and synthetic CRUD. Rehearse both rollback cases below, including D1-to-Postgres restore.

9. **Prepare traffic switching before the freeze.** Determine whether Percy owns the hostname. On an existing Cloudflare-proxied owned hostname, a tested Worker Route over the Railway origin can provide a reversible traffic switch without changing resolver targets; test origin fallback/TLS and route precedence first. Otherwise prepare a Workers Custom Domain on an owned Cloudflare zone, preserving old DNS records and lowering TTL in advance where applicable. Rehearse certificate issuance/conflicting-record handling on a staging hostname. A Railway-owned `*.up.railway.app` hostname cannot simply have its DNS transferred to Percy. If that is the only URL, retain Railway to redirect/forward safely or introduce an owned canonical hostname before migration. Do not promise invisible URL continuity without ownership.

10. **Deploy the release candidate with writes closed.** Use the verified schema and release artifact against the empty production candidate D1, at a restricted verification hostname. Confirm DB identity/readiness. Keep Railway production authoritative. Finish all dependency/build work now so the freeze contains only data copy, verification, and traffic switching.

11. **Freeze writes at the source, briefly.** Announce a low-traffic maintenance window, initially budgeting 5–10 minutes but using measured rehearsal duration. Reads remain available. Enforce a server-side gate covering every mutating route, server action, direct Railway hostname, and older deployment reachable by players; a disabled button is insufficient. Return a clear retryable maintenance response without queuing hidden mutations. Drain in-flight writes and verify no remaining writer, scheduled job, or admin task can alter Postgres. D1 stays closed to player writes too. If the gate requires a Railway patch, deploy and test that small compatibility patch before the migration window. Do not build dual-write or CDC machinery for hundreds of rows.

12. **Take the final snapshot and import.** Export all five tables and all live columns in one consistent read-only Postgres snapshot, with counts and canonical hashes. Retain the source backup and export manifest securely. Import into the empty production candidate in dependency order. Fail closed on any error. Compare every row and field against the source snapshot, check foreign keys, uniqueness, aggregates, API read responses, and old bookmarked IDs. Confirm no rehearsal/test records are present. A partial import is never eligible for traffic.

13. **Switch traffic while both sides remain write-fenced.** Activate the rehearsed route/custom-domain change and verify TLS, assets, representative pages, and database-backed reads through the public hostname. Old cached clients may still reach Railway: keep its write fence in place throughout, then redirect users to the canonical Cloudflare URL where practical. Verify direct Workers/preview hostnames cannot bypass the production write gate. Do not weight traffic across independent writable Postgres and D1 backends.

14. **Open the sole D1 writer.** Only after exact reconciliation and public smoke checks pass, enable Cloudflare mutations. Record this timestamp as the rollback boundary. Refresh old clients to avoid stale Next/vinext assets and API contracts. Keep Railway fenced and operational as a fallback. Observe closely through the next actual league session; keep Railway/Postgres and backups at least seven days and until a restore drill and owner acceptance are complete. Retain longer-lived exports beyond platform recovery windows. Production promotions should remain deliberate until this soak completes.

15. **Rollback or retire deliberately.** Apply the triggers below. Once stable, close superseded infrastructure work with attribution, update operational docs, and only then cancel Railway services. Do not delete the source database merely because the first deployment returned 200.

### Explicit rollback triggers and procedures

* **Before switching:** any schema/column mismatch, row/hash mismatch, lost icon data, FK failure, wrong binding, failed seed rollback, failed core CRUD, or unresolved build/deploy issue is a no-go. Stay on Railway. If the freeze exceeds 10 minutes without a clearly imminent verified finish, abandon that window, leave Cloudflare closed, reopen Railway, and take a fresh snapshot next time.
* **After switching but before accepting D1 writes:** any failed core flow, TLS/asset failure, or database-read failure triggers switchback. Restore the recorded route/DNS and confirm Railway reads, then reopen Railway writes. There is no D1 user data to merge. DNS propagation may delay client recovery; keep the target's write fence closed and show retry guidance.
* **After D1 has accepted writes:** immediately fence D1 for any confirmed lost/corrupt accepted write or cross-record inconsistency. Also fence and investigate if two consecutive minute-spaced database readiness probes fail, or core CRUD repeatedly fails for a player; do not wait for statistical percentages with this small audience. Choose a validated Worker-only rollback if compatible with the current D1 schema. Otherwise freeze both systems, drain requests, export the authoritative D1 state, and reverse-migrate into an isolated Postgres restore first. Validate counts/hashes/IDs/booleans/timestamps and current-main compatibility, then restore that verified state to Railway's database under a transaction while no writers are active. Switch traffic back and reopen only Railway. Preserve both pre-rollback backups. If reverse migration cannot be validated, keep writes closed and repair forward. **Never point users back to stale Postgres and discard D1 writes.** A database rollback and a Worker version rollback are separate actions.

## Data migration design

Use a small, reviewed **offline export/transform/verify script producing a canonical JSON manifest and SQLite-compatible data-only SQL**, then load it with a pinned `wrangler d1 execute <target> --remote --file <data.sql>` (or a version-verified equivalent `cf` command). No production app endpoint is needed. A raw `pg_dump` is a backup, not a D1-compatible import: Postgres types, COPY syntax, defaults, and migration metadata are not portable. API replay would regenerate IDs/timestamps, seed extra cards, omit fields, and retrigger increments; it is unsuitable for authoritative transfer. Cloudflare documents file import/export separately from schema tooling: [D1 import/export](https://developers.cloudflare.com/d1/best-practices/import-export-data/).

| Data | Required mapping/check |
|---|---|
| All IDs | Copy existing Prisma cuid strings verbatim into TEXT PK/FK columns. Never regenerate or require UUID syntax. New UUIDs from the PR can coexist with old cuid values; reverse migration must accept both. Preserve bookmarked profile/deck URLs. |
| Profile | Include `id`, `name`, `createdAt`, **`iconCard` when present live**, and any newly discovered columns. Abort on unmapped live columns rather than dropping them. Preserve exact text and nulls. |
| CollectionCard | Preserve `id`, `profileId`, `name`, `qty`, `owned`; no reseeding, catalog filtering, renaming, or quantity aggregation during migration. Unknown imported card names are legitimate data. |
| Deck | Preserve ID, owner, name, nullable commander, creation time. |
| DeckCard | Preserve ID, deckId, name, quantity and `isBasic`. |
| Match | Preserve all IDs, note/null, creation time. Winner/loser deck IDs are nullable plain text in both inspected schemas, not deck FKs. Report dangling historical deck references; do not silently delete matches or invent stronger constraints during transfer. |
| Timestamps | Main initial SQL uses `TIMESTAMP(3)` without timezone. Establish the actual production convention first; do not assume the operator's Asia/Hong_Kong timezone. Export UTC instants consistently and normalize to fixed-width `YYYY-MM-DDTHH:mm:ss.SSSZ`, preserving milliseconds. Verify sample instants against current API output. PR defaults use SQLite `CURRENT_TIMESTAMP`, a different text shape: explicitly write canonical ISO values for all new rows and align defaults before relying on textual sorting. |
| Booleans | Map Postgres booleans explicitly to SQLite integers 1/0; map back explicitly on rollback. Do not import strings such as `"false"`, which can be truthy in JS. Verify Drizzle returns JSON booleans. |

Export all tables in one read-only repeatable-read transaction after fencing/draining; independent table exports during active writes are not a consistent snapshot. Capture source commit/schema fingerprint, export time, each table's row count, ordered canonical rows and SHA-256, and the transform version. Do not include credentials in the manifest. Check the actual dataset size rather than relying on “hundreds”; seeded collections can already exceed that estimate.

Apply schema first. Import parents before children: `Profile`, `CollectionCard`, `Deck`, `DeckCard`, `Match` (Deck may also precede CollectionCard). Generate explicit column lists and small INSERT statements, escaping apostrophes and preserving Unicode/newlines/nulls. Validate the generated SQL against an isolated database and compare its data back to canonical JSON. Literal SQL avoids bound-parameter counts, but still has statement-size limits. Alternatively a parameterized D1 REST importer is reasonable, with <=100 parameters per statement and checked results; its HTTP batching guarantees must not be assumed identical to the Worker binding API.

**Do not rely on a whole SQL file being one transaction.** The target is empty, private, and ineligible for promotion until full verification. On partial failure, retain diagnostics and rebuild a new empty candidate; do not retry additive writes into a dirty database or use `INSERT OR IGNORE` to conceal errors. This gives safe repeatability without requiring an application-wide live import transaction. Keep schema migration history in D1, but do not import Prisma's `_prisma_migrations` as application data.

Verification must compare full canonical rows sorted by primary key, not counts alone: IDs, quantities, owned/basic flags, icon choices, notes, nulls, and timestamps. Run `foreign_key_check` and integrity checks, compare per-profile collection totals/deck counts, per-deck card totals, and match win/loss totals. Compare API responses after intentional representation normalization. Test source backup restoration and reverse conversion before the production window. Since rows have no general updatedAt/deletion journal, a full frozen copy in either direction is safer than guessing deltas.

## Missed risks and deployment verdict

### The workflow cannot deliver a working migration as written

`.github/workflows/deploy.yml` is not an acceptable production rollout. It runs migrations before deployment, with no creation, transfer, readiness, rollback, preview, or concurrency gate. If its `D1_DATABASE_ID` points at the supplied nonexistent UUID, the migration step fails. Strictly, the workflow reads that secret rather than reading the UUID from TOML: its undisclosed value could differ. Pointing the secret elsewhere would still leave unproven agreement between migration target and the `cloudflare.config.ts` binding by name. A successful migration command alone would not prove the deployed Worker uses that database.

There is **no committed Vite configuration** registering the vinext/Cloudflare/RSC setup, despite scripts using bare `vite` and `vinext-cloudflare deploy`. Official integration guidance requires initialized Vite configuration and says deploy validates/builds that setup. This is an independent expected build/deploy blocker, not just a missing secret. No build was run, so the exact first error is unmeasured. Resolve against the locked `vinext@1.0.0` and `@vinext/cloudflare@1.0.0`; do not assume the deployment CLI repairs configuration. [Official vinext setup/deployment guidance](https://github.com/cloudflare/vinext/blob/main/README.md).

Do not label `npx cf ... --dir drizzle` invalid merely because Wrangler uses different flags. `cf` is installed by this PR. Its locked CLI behavior, remote default, noninteractive behavior, and config selection need verification in the implementation pass. Use a single tested CLI path, not mixed assumptions about cf and Wrangler. The README's token instructions mention only Workers edit, omitting D1 edit required by migration. Handwritten binding types may hide integration problems even when `tsc` succeeds.

### D1 semantics are a correctness constraint

The documented cap is 100 bound parameters per statement, not per transaction; batching does not rescue an oversized individual INSERT. Free-tier Workers have a documented 50-query invocation limit, so hundreds of sequential import updates also deserve an explicit request budget. D1 also bounds SQL statement length and query duration; test the exact chunked path remotely. Free-tier Time Travel retains seven days, so it is not a long-term backup strategy. [D1 limits](https://developers.cloudflare.com/d1/platform/limits/).

The Workers binding's `batch()` executes an atomic sequence and rolls it back on statement failure; it is a suitable replacement for this precomputed seed operation. It is not Prisma's interactive read/write callback transaction. Constraint checks must remain authoritative under races. [D1 batch API](https://developers.cloudflare.com/d1/worker-api/d1-database/).

The supposedly redundant `0001` migration is potentially dangerous on populated D1: it uses `PRAGMA foreign_keys=OFF`, then drops/recreates Deck and Profile. D1's implicit transactions prevent that pragma from disabling enforcement; dropping parent tables with cascades can remove dependent rows. Deferring constraint checks is not a blanket suppression of cascades. Thus never run this rebuild over imported/live data, and do not “fix” it by simply substituting a pragma. [D1 foreign-key behavior](https://developers.cloudflare.com/d1/sql-api/foreign-keys/).

### Framework/runtime and limits

This PR changes framework/build system, runtime, ORM, database engine, and deployment together. Its beta cf/Vite-plugin dependencies add integration risk even if vinext itself is locked at 1.0.0. Do not turn old launch-era “experimental” descriptions into a claim about today's exact release; assess the locked stack through deployed parity tests. A Next-compatible API is not proof of identical caching, RSC, error, or routing behavior. If blockers persist, keep Railway and reconsider scope rather than forcing a deadline-driven cutover.

`import { env } from "cloudflare:workers"` is supported in Workers; it is not inherently a defect. It requires the Workers runtime/integration rather than plain Node's module loader, and database I/O still belongs in request context. Test server-rendered pages as well as API routes; do not let build-time prerendering unexpectedly query production. [Cloudflare binding imports](https://developers.cloudflare.com/workers/runtime-apis/bindings/).

The static `/api/health` says nothing about DB binding/schema correctness. Add an operational readiness check without exposing secrets. Do not enable read replication or additional caching during this migration; if later enabled, establish read-after-write behavior explicitly. Ensure app/API responses are not accidentally cached stale.

Request volume and row quotas are probably sufficient, but **bundle size and CPU may be the binding limits** for an SSR framework. Measure compressed Worker bundle, startup and per-request CPU in the actual free-tier deployment. Check generated static asset count and per-file sizes against current plan limits, and ensure ASSETS routing does not swallow API/SSR paths. Keep card artwork external as it is now rather than bulk-uploading it in this migration. `IMAGES` is declared although the inspected card component uses ordinary images; verify need/availability and remove unused binding requirements in implementation. [Workers platform limits](https://developers.cloudflare.com/workers/platform/limits/).

### DNS, security, and collaboration

Workers Custom Domains require control of a suitable Cloudflare zone and involve DNS/certificate provisioning. Existing DNS records can conflict; saving records and rehearsing restoration matter. A route over a proxied Railway origin can be a safer transitional switch than simultaneous nameserver migration. If the domain is not already on Cloudflare, move/verify DNS as a separate preliminary operation. [Workers Custom Domains](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/).

The no-auth app makes accidental preview writes and two writable URLs especially dangerous. Access protection for rehearsal and origin-level write fencing address that migration risk without broadening this into an authentication rewrite. Never shadow/replay live mutating requests into both databases. Shadow reads and disposable fixture writes are sufficient.

Do not make cost savings depend on immediately deleting the fallback. The small extra overlap cost buys a restore path. Likewise, taking ownership does not require erasing wd's work: a credited continuation preserves useful implementation and avoids concurrent edits on someone else's branch.
